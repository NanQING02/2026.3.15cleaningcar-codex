## 1. 推理日志精简与调试画面瘦身

- 目标
  - 收紧 Web 默认展示的推理日志量，只保留关键事件和低频性能摘要
  - 降低实时调试画面持续写 JPEG、前端持续轮询带来的性能消耗
- 当前现状
  - Web 当前通过 `GET /logs/inference` 读取日志
  - 调试预览仍是“推理端周期写图 + Web 端轮询读取”的文件式方案
  - 日志与预览默认打开时，对 CPU、磁盘和前端刷新都有额外开销
- 为什么要做
  - 当前日志量过大，影响故障判断效率
  - 长期开启调试预览不适合作为正式生产模式默认行为
- 预期改动范围
  - `web/server.py`
  - `web/helpers.py`
  - `web/templates/zone_editor.html`
  - `cleaningcar/pipeline.py`
  - `config_manager.py`
- 可能影响的接口/配置/页面
  - `GET /logs/inference`
  - Web 日志面板
  - Web 调试画面区域
  - 新增或收口调试开关，例如 `video.debug_preview_enabled`
- 验收点
  - Web 默认只看关键事件和低频性能摘要
  - 原始完整日志仍可保留，但不再默认高频轮询
  - 关闭调试画面后，不再持续写调试帧
  - 对正式运行的 CPU、磁盘和页面刷新压力有可见下降
- 当前待确认项
  - 关键事件日志的最终口径
  - 性能摘要的展示间隔
  - 调试预览是否只保留手动刷新，还是保留低频自动刷新

## 2. 多配置多路推理产品化

- 目标
  - 让多路推理的启停、查看、切换和运行时资源隔离变得清晰、稳定、可交付
- 当前现状
  - 当前推理接口已经支持 `key` 参数
  - `POST /inference/start`、`POST /inference/stop`、`POST /inference/restart`、`GET /inference/status`、`GET /inference/health` 已具备按配置实例管理的基础
  - 但多实例共用路径、命令目录、心跳文件、截图目录等资源时，仍需要进一步产品化收口
- 为什么要做
  - 现在可以“跑起来”，但还不够适合甲方长期切换和运维
  - 多路实例如果共享运行时路径，后续容易产生互相串扰
- 预期改动范围
  - `web/inference.py`
  - `web/server.py`
  - `web/templates/zone_editor.html`
  - `config_manager.py`
  - `cleaningcar/runtime_signals.py`
- 可能影响的接口/配置/页面
  - 现有 `/inference/*` 系列接口
  - 可能新增实例总览接口，例如 `/inference/instances`
  - Web 配置切换与实例状态总览区域
  - 运行时目录相关配置项
- 验收点
  - 多个配置实例能清晰列出、独立启停、独立查看健康状态
  - 命令目录、心跳路径、启动截图、手动截图、事件输出等运行时资源互不串扰
  - 配置冲突时，启动前就能给出明确提示
- 当前待确认项
  - 第一版是否只支持“多配置并行”，暂不做“单配置复制多实例”
  - 默认隔离策略是强制显式配置，还是按配置名自动派生目录

## 3. 按车辆 ID 录像浏览优化

- 目标
  - 让 `per_id` 录像浏览从“全量扫目录、一次性返回”改成适合长期运行的索引化、分页化方案
- 当前现状
  - 当前已有 `GET /videos/per_id`
  - 当前已有 `GET /videos/per_id/file`
  - Web 页面会直接读取录像列表，现阶段更偏向简单可用，规模变大后会拖慢页面
- 为什么要做
  - 录像积累后，全盘扫描与全量返回会越来越重
  - 浏览、筛选、定位异常录像的效率还不够高
- 预期改动范围
  - `web/server.py`
  - `web/helpers.py`
  - `web/templates/zone_editor.html`
  - 录像输出或事件落盘相关索引逻辑
- 可能影响的接口/配置/页面
  - `GET /videos/per_id`
  - `GET /videos/per_id/file`
  - Web 录像浏览区域
  - 可能新增索引文件或元数据字段
- 验收点
  - 录像列表支持分页
  - 支持按配置、车牌、车辆 ID、时间段、异常类型等筛选
  - 页面初次加载不再触发全目录重扫
  - 在线预览与下载入口保持可用
- 当前待确认项
  - 索引文件格式
  - 是否把异常事件信息同步写入录像索引
  - 页面优先展示最近记录，还是支持多维排序

## 4. 性能专项优化与验收基线

- 目标
  - 在不改业务口径的前提下，优先压掉当前最明显的无效开销，并形成板端可重复执行的性能验收基线
- 当前现状
  - 项目已经稳定可跑，但仍存在日志轮询、调试画面写图、录像浏览扫描等非主推理开销
  - 当前还缺少统一的“优化顺序 + 验收基线”文档化口径
- 为什么要做
  - 后续功能继续叠加前，先把板端性能基线定义清楚
  - 否则每次改动都难以判断是功能问题还是性能退化
- 预期改动范围
  - `cleaningcar/pipeline.py`
  - `web/server.py`
  - `web/templates/zone_editor.html`
  - `web/inference.py`
  - 与性能监控、日志、预览、录像列表相关的模块
- 可能影响的接口/配置/页面
  - `/inference/health`
  - `/inference/status`
  - `/logs/inference`
  - 调试画面、日志面板、录像浏览面板
- 验收点
  - 单路 RTSP 长时间运行下，`/inference/health` 保持 `ok`
  - `restart_count` 不异常增长
  - 心跳帧号持续推进
  - 事件链路、截图链路、单车视频链路仍保持成立
  - 调试和日志相关开销比当前版本更低
- 当前待确认项
  - 第一批优先优化项的顺序
  - 正式验收时的 CPU、内存、FPS 目标区间
  - 是否需要把性能摘要做成按钮触发，还是低频自动汇总

## 5. 事件触发机制修改

- 目标
  - 对当前事件触发逻辑做规则层面的重新梳理和收口，但本轮先只建任务卡，不提前写新规则
- 当前现状
  - 当前触发链路主要落在：
    - `cleaningcar/events.py`
    - `cleaningcar/pipeline.py`
    - `zone_manager.py`
  - 当前事件触发不是单点判断，而是由区域状态、进出标志、轨迹状态、驻留时长、方向解析、洗车确认状态等共同参与
  - 当前事件类型与允许项受 `allowed_events` 等逻辑控制
- 为什么要做
  - 现有触发链路已经可运行，但若后续要改规则，需要先把现状边界写清，避免直接改乱
  - 事件规则属于业务口径核心，必须先把“当前怎么触发”与“将来准备改什么”分开记录
- 预期改动范围
  - `cleaningcar/events.py`
  - `cleaningcar/pipeline.py`
  - `zone_manager.py`
  - 可能连带影响事件 JSON 字段和 Web 事件展示
- 可能影响的接口/配置/页面
  - 事件 JSON 输出
  - Web 事件查看区域
  - 事件开关、区域参数、方向判断相关配置
- 验收点
  - 新规则确认后，事件类型、触发条件、方向判断和去重口径都能稳定复现
  - 事件修改不会破坏现有截图链路和主推理链路
  - 板端复测时，事件输出与业务预期一致
- 当前待确认项
  - 待你确认的规则：
    - 事件类型是否增删
    - 各事件的触发前置条件
    - Zone A / Zone B / 流向 / 驻留时长 / 洗车状态各自参与到什么程度
    - 是否保留当前单生命周期去重口径

### 当前事实记录

- 当前入口在 `cleaningcar/events.py` 的 `update_track(...)`
- `emit_event(...)` 负责最终事件输出
- `zone_manager.py` 中的 `update_track(...)` 和 `resolve_direction(...)` 参与区域状态与方向判定
- 当前逻辑已经使用以下条件共同参与触发：
  - `allowed_events`
  - `disable_plate_only_events`
  - `single_lifecycle_events`
  - Zone A / Zone B 进出状态
  - 流向判断
  - 轨迹帧数与驻留时长
  - `water_detected`
  - `washing_confirmed`
  - `just_confirmed`
