# 已完成开发与使用说明

本文档是 `docs/规划记录/` 下“已完成部分”的主入口，按当前仓库实现汇总已经落地的功能、使用方式、配置位置和板端验收要点。

建议阅读顺序：

1. 先看本文档，确认当前项目已经具备什么能力、入口在哪里
2. 需要追溯历史实施细节时，再看同目录下的历史记录文档
3. 还未开发的事项，转看 `待开发事项总表.md`

## 1. 参数分级与 Web 配置收口

- 功能目标
  - 让甲方只修改基础业务参数即可使用，算法阈值、调试开关、运行时路径等保留在开发者层
- 当前状态
  - 已落地
- 代码落点
  - `web/config_tiers.py`
  - `web/server.py`
  - `web/templates/zone_editor.html`
- 用户怎么用
  - Web 基础面板只改用户参数
  - 开发者面板单独管理开发者参数
  - 接口口径已经拆成：
    - `GET /config`
    - `GET /config/schema`
    - `GET /config/user`
    - `POST /config/user`
    - `POST /config/developer`
- 涉及的配置项
  - 用户参数示例：
    - `system.device_id`
    - `system.api.*`
    - `video.source`
    - `video.source_mode`
    - `video.hw_decode`
    - `video.workers`
    - `video.core_mask`
    - `logic.lane_name`
    - `zones.*`
    - `logic.enable_per_id_video`
    - `logic.per_id_video_dir`
  - 开发者参数示例：
    - `video.fp_output_mode`
    - 各类阈值与锁定参数
    - 调试画面与运行时路径
    - 清理策略参数
    - 心跳、命令、启动信号相关路径
- Web/脚本/命令入口
  - 手工启动 Web：
    ```bash
    source venv-gst/bin/activate
    ./start_web_server.sh start
    ```
  - 读取用户参数：
    ```bash
    curl http://127.0.0.1:8000/config/user
    ```
- 板端怎么验收
  - 基础面板保存时，只应写入用户参数白名单
  - 若在用户面板提交开发者字段，后端应拒绝保存
  - `GET /config/user` 返回内容应与基础面板展示一致

## 2. 运行检测 / 死机自启 / 心跳 guardian

- 功能目标
  - 让推理进程具备心跳、进度检测和异常重启能力，减少板端卡死后无人值守的问题
- 当前状态
  - 已落地
- 代码落点
  - `cleaningcar/runtime_config.py`
  - `cleaningcar/runtime_signals.py`
  - `cleaningcar/pipeline.py`
  - `web/inference.py`
  - `web/server.py`
- 用户怎么用
  - 从 Web 控制台启动推理即可，guardian 会自动接管健康检查
  - 本地文件视频在 `auto_restart=false` 时只跑一遍后退出，不会循环重放
  - RTSP 等连续流在异常卡死时会按 guardian 规则回收并重启
- 涉及的配置项
  - `system.heartbeat_path`
  - `system.metrics_path`
  - `system.command_dir`
- Web/脚本/命令入口
  - 查看运行状态：
    ```bash
    curl http://127.0.0.1:8000/inference/status
    curl http://127.0.0.1:8000/inference/health
    ```
  - Web 接口：
    - `POST /inference/start`
    - `POST /inference/stop`
    - `POST /inference/restart`
    - `POST /inference/auto_restart`
- 板端怎么验收
  - 连续运行 10 到 15 分钟时，`/inference/health` 维持 `ok`
  - `restart_count` 不异常增长
  - 心跳中的 `total_frames`、`latest_frame_idx` 持续推进
  - 本地文件视频在关闭自动重启时，跑完一遍后自动结束

## 3. 启动信号与启动截图

- 功能目标
  - 在推理成功启动后给出明确启动信号，便于外部程序、运维和验收人员确认系统已进入工作状态
- 当前状态
  - 已落地
- 代码落点
  - `config_manager.py`
  - `cleaningcar/runtime_signals.py`
  - `cleaningcar/pipeline.py`
- 用户怎么用
  - 推理完成首批有效处理后，会写启动标志并保存一张启动截图
  - 启动截图是自动行为，不是手动截图命令
- 涉及的配置项
  - `system.startup_flag_path`
  - `system.startup_capture_dir`
- Web/脚本/命令入口
  - 无单独 Web 按钮，属于推理启动后的自动链路
- 板端怎么验收
  - 首次启动推理后，启动标志文件应存在
  - `captures/startup/` 下应生成启动截图
  - 重新启动推理时应再次产生新的启动记录

## 4. 手动保留截图命令与接口

- 功能目标
  - 允许运维或验收时随时保存当前画面，便于留档和问题回溯
- 当前状态
  - 已落地
- 代码落点
  - `cleaningcar/runtime_signals.py`
  - `cleaningcar/pipeline.py`
  - `web/models.py`
  - `web/server.py`
- 用户怎么用
  - Web 端可直接调用手动截图接口
  - 运行中的推理进程也支持通过命令目录投递 `keep_snapshot`
  - 支持保留原图和标注图
- 涉及的配置项
  - `system.command_dir`
  - `system.manual_capture_dir`
- Web/脚本/命令入口
  - `POST /snapshot/keep`
  - 命令目录中的 `keep_snapshot`
- 板端怎么验收
  - 调用 `POST /snapshot/keep` 后，`captures/manual/` 下应生成新截图
  - 截图文件应真实存在，且能对应当前画面

## 5. 事件截图修复

- 功能目标
  - 解决“事件有、但 `captureImage` 为空或文件不存在”的问题，让事件 JSON 与截图真实落盘保持一致
- 当前状态
  - 已落地
- 代码落点
  - `cleaningcar/events.py`
  - `config_manager.py`
- 用户怎么用
  - 无需手工操作，属于事件输出链路的自动修复
  - 现在只有截图真实写入成功时，事件 JSON 才会写入有效的 `captureImage`
- 涉及的配置项
  - `event_output_dir`
  - `event_capture_dir`
- Web/脚本/命令入口
  - 事件 JSON 落在 `events/<配置名>/`
  - 事件截图落在 `captures/<配置名>/`
- 板端怎么验收
  - 触发事件后，检查事件 JSON 的 `captureImage` 非空
  - 按 `captureImage` 对应路径检查文件必须真实存在
  - 截图失败时日志中应能看到事件类型、轨迹 ID、目标路径和失败原因

## 7. 清理策略

- 功能目标
  - 防止截图和单车视频长期堆积，占满板端存储
- 当前状态
  - 已落地
- 代码落点
  - `cleaningcar/storage_cleanup.py`
  - `cleaningcar/pipeline.py`
  - `config_manager.py`
- 用户怎么用
  - 主流程会按周期自动执行清理
  - 当前清理范围只覆盖截图和单车视频，不清理事件 JSON、日志、模型和配置
- 涉及的配置项
  - `storage.clean_interval_seconds`
  - `storage.capture_keep_days`
  - `storage.capture_keep_count`
  - `storage.per_id_video_keep_days`
  - `storage.per_id_video_keep_count`
- Web/脚本/命令入口
  - 无单独 Web 控件，属于后台周期任务
- 板端怎么验收
  - 构造超期截图或单车视频后，下一轮清理应删除最旧文件
  - `captures/startup/` 与 `captures/manual/` 至少保留最新 1 次
  - 清理异常时不应影响推理、事件和截图主链路

## 8. Web 脚本收口与 systemd 服务化

- 功能目标
  - 把部署入口和服务入口收口成少量固定脚本，降低板端交付和运维复杂度
- 当前状态
  - 已落地
- 代码落点
  - `install_runtime_venv.sh`
  - `start_web_server.sh`
  - `uninstall_runtime_venv.sh`
  - `install_cleaningcar_systemd.sh`
  - `systemd/cleaningcar-web.service`
- 用户怎么用
  - 环境安装：
    ```bash
    bash ./install_runtime_venv.sh
    ```
  - 手工启动 Web：
    ```bash
    source venv-gst/bin/activate
    ./start_web_server.sh start
    ```
  - 查看 Web 状态：
    ```bash
    ./start_web_server.sh status
    ```
  - 安装为 `systemd` 服务：
    ```bash
    bash ./install_cleaningcar_systemd.sh
    ```
  - 卸载运行环境：
    ```bash
    bash ./uninstall_runtime_venv.sh
    ```
- 涉及的配置项
  - `configs/config.json`
  - Web 监听地址与端口参数
  - `systemd/cleaningcar-web.service` 中的服务启动配置
- Web/脚本/命令入口
  - 手工模式由 `start_web_server.sh` 负责 `start|stop|restart|status`
  - 服务模式由 `cleaningcar-web.service` 托管 Web 主进程
- 板端怎么验收
  - `bash ./install_runtime_venv.sh` 执行后不应自动启动推理
  - `./start_web_server.sh start` 后，8000 端口应正常监听
  - `systemctl stop cleaningcar-web` 后服务保持停止
  - 直接异常杀掉 Web 主进程时，`systemd` 应按 `Restart=on-failure` 自动拉起
