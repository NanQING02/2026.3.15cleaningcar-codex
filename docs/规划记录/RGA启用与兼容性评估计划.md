# RGA 启用与兼容性评估计划

## 1. 背景与当前结论

目标是评估项目是否适合在正式板端启用 RGA 缩放，以降低预处理的 CPU 开销和资源占用。

基于当前仓库状态，先给出结论：

- 当前正式推理主链路没有接入 RGA
- 仓库里现有的 RGA 代码属于实验模块，不在正式调用链中
- 当前仓库没有提供完整的 RGA 运行产物，不能直接把“启用 RGA”当成现成功能交付
- 甲方设备上容易报错是合理现象，原因大概率不是 Python 逻辑本身，而是板端运行环境与实验室环境不一致

因此，后续如果要做，正确顺序应当是：

1. 先做板端能力探测和独立验证
2. 再做可选启用
3. 最后再做性能对比和正式切换

当前不建议直接把 RGA 并入正式主链路。

## 2. 仓库现状

### 2.1 当前 RGA 相关代码位置

- `future_modules/acceleration/rga_resize_plugin.py`
  - 这是当前仓库里唯一明确的 RGA Python 封装入口
  - 通过 `ctypes.CDLL()` 加载 `future_modules/acceleration/rga_wrapper/libcleaningcar_rga.so`
  - 调用失败时会回退到 `cv2.resize(...)`
- `future_modules/legacy_detection/vision_legacy.py`
  - 这里会尝试导入 `rga_resize_plugin.py`
  - 仅属于旧检测实验链路，不在当前正式主流程中

### 2.2 当前正式主链路的实际情况

当前正式链路里没有检索到 `future_modules.acceleration` 或 `rga_resize_plugin` 的调用。

正式链路仍主要使用 `cv2.resize(...)`，至少包括以下位置：

- `cleaningcar/fp_detect.py`
- `cleaningcar/pipeline.py`
- `cleaningcar/events.py`
- `cleaningcar/plate_lpr.py`

这说明当前版本即使板端上装了 RGA 相关库，也不会自动用上。

### 2.3 当前仓库缺失的关键运行条件

当前仓库中已确认：

- 不存在 `future_modules/acceleration/rga_wrapper/`
- 不存在 `future_modules/acceleration/rga_wrapper/libcleaningcar_rga.so`
- `packages/` 下当前只有 `im2d.h`，没有 `librga.so`

而 `install_runtime_venv.sh` 的逻辑是：

- 如果 `packages/librga.so` 存在，才复制到 `/usr/local/lib/librga.so`
- 如果 `packages/im2d.h` 存在，才复制到 `/usr/local/include/rga/im2d.h`

也就是说，当前脚本只是“支持安装 RGA 依赖”，并不等于“当前仓库已经自带完整 RGA 依赖”。

## 3. 为什么实验室设备能跑，甲方设备容易报错

结合当前仓库状态，最可能的原因有以下几类：

- 实验室设备本机已经预装过 `librga.so`
- 实验室设备本机曾放置过 `libcleaningcar_rga.so`，而甲方设备没有
- 两边的板卡镜像、内核驱动、RGA 运行库版本不一致
- 动态库搜索路径不同，导致实验室设备能找到 so，甲方设备找不到
- wrapper so 即使存在，也可能与甲方设备上的 `librga.so` 或驱动 ABI 不匹配

因此，“实验室能跑”并不能说明“仓库已经具备正式接入条件”。

## 4. 正式接入 RGA 的建议原则

后续接入时，建议固定遵守以下原则：

- 默认关闭
  - 正式配置默认仍走 `cv2`
- 启动即探测
  - 启动时明确判断 RGA 是否可用，不要在主链路里隐式失败
- 失败自动回退
  - RGA 初始化失败、运行失败、尺寸转换失败时，必须自动回退 `cv2.resize(...)`
- 不影响主流程
  - RGA 失败不能拖死推理、截图、事件、录像链路
- 日志要收口
  - 只打必要日志，避免每帧刷 RGA 错误
- 配置要可控
  - 后续如果新增配置，建议区分“自动尝试”和“强制启用”两种模式

建议后续配置口径采用以下形式之一：

- `cv2`
  - 强制使用 OpenCV
- `rga_auto`
  - 可用则启用，不可用自动回退
- `rga_force`
  - 仅用于实验验证；探测失败直接报错退出

当前阶段推荐目标是 `rga_auto`，不建议一上来就走 `rga_force`。

## 5. 建议的实施顺序

### 阶段 1：板端能力探测

目标：

- 先判断甲方设备到底缺什么，而不是直接改主链路

建议检查项：

- `libcleaningcar_rga.so` 是否存在
- `librga.so` 是否存在
- `ldd libcleaningcar_rga.so` 是否有缺失依赖
- RGA 最小缩放调用是否可成功执行
- 成功后输出一次明确的环境摘要

阶段 1 输出物建议：

- 一份板端探测脚本或最小验证脚本
- 一份探测结果日志模板

### 阶段 2：可选接入正式链路

目标：

- 在不破坏现有功能的前提下，把 RGA 接入到单一明确热点

建议从最值得替换的预处理点开始，而不是一次性替换所有 `cv2.resize(...)`。

优先候选：

1. 检测前处理的缩放链路
2. 单车视频写出前的缩放链路
3. 事件截图输出前的缩放链路

不建议第一轮就改：

- 车牌识别的全部内部 resize
- 所有非关键路径 resize

### 阶段 3：性能对比与板端验收

目标：

- 确认 RGA 不是“能跑但不值”，而是确实带来收益

建议对比项：

- 单路 RTSP 稳定运行时的 CPU 占用
- 内存占用
- 推理 FPS
- `/inference/health` 是否稳定为 `ok`
- `restart_count` 是否异常增长
- 事件、截图、单车视频是否仍正常

## 6. 板端验收清单

后续真正开工后，建议按下面顺序验收：

1. 先验环境
   - 检查 `libcleaningcar_rga.so` 是否存在
   - 检查 `librga.so` 是否存在
   - 检查 `ldd` 是否无缺失依赖
2. 再验最小功能
   - 独立执行一次 RGA resize smoke test
   - 明确成功、失败、回退三种日志
3. 再验正式链路
   - 开启推理后确认功能不变
   - 观察事件、截图、录像、Web 状态是否正常
4. 最后验收益
   - 和纯 `cv2` 方案对比 CPU、FPS、稳定性

## 7. 当前不直接开工的原因

当前先写文档、不直接改代码，是因为还存在以下基础问题：

- 当前正式主链路并未接 RGA
- 当前仓库没有完整的 RGA 运行产物
- 板端兼容问题还没有形成可复现的最小探测路径
- 如果直接硬接到主流程，风险是甲方环境一报错就影响正式推理

因此，下一步最合理的开工顺序是：

1. 先补板端探测与最小验证
2. 再做 `rga_auto` 可选接入
3. 再做性能复测和是否默认启用的决策

## 8. 与当前待开发事项的关系

本事项属于“性能专项优化与验收基线”的子方向，但因为板端兼容性风险高，单独立项记录。

后续如果正式开工，建议把它作为性能优化中的独立子任务处理，而不是和日志精简、调试画面瘦身一起混做。
