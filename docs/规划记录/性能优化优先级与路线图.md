# 性能优化优先级与路线图

## 1. 目标

这份文档只做一件事：

- 基于当前仓库真实实现，整理“哪些性能项值得做”
- 按“最方便先做”和“性价比/优化力度最大”两个维度排优先级
- 给出建议开工顺序，避免一上来就碰高风险项

当前口径：

- 先优先压掉非核心业务开销
- 不为了性能破坏现有事件、截图、录像、车牌和车型链路
- 推理主链路的高风险改动放到后面

## 2. 当前已经确认的性能热点

以下结论都来自当前仓库代码，不是泛泛猜测。

### 2.1 调试画面写图

当前 `cleaningcar/pipeline.py` 会按 `video.debug_frame_interval` 周期性执行：

- `cv2.imwrite(str(debug_frame_file), frame_out)`

对应现状：

- 默认配置里 `video.debug_frame_path` 已开启
- 默认配置里 `video.debug_frame_interval = 30`
- Web 页面通过 `/debug_frame_meta` 和 `/debug_frame` 读取这张调试图

这类开销属于：

- 持续磁盘 I/O
- 持续 JPEG 编码
- 前端持续读取

如果甲方运行时一直开着，这是非常典型的“先优化掉”的项。

### 2.2 单车录像 `per_id` 写出

当前 `cleaningcar/pipeline.py` + `cleaningcar/video_io.py` 的链路里：

- `logic.enable_per_id_video = true`
- 默认目标分辨率是 `1920x1080`
- 默认 `logic.per_id_fps = 20`
- 默认 `logic.per_id_frame_stride = 1`
- 每帧写入 `FfmpegH264Writer`
- writer 通过 `ffmpeg` 子进程持续吃原始 `bgr24` 数据

这类开销属于：

- 每帧 resize
- 每帧原始图像写管道
- 持续编码
- 持续落盘

这是当前最重、但也最容易通过参数先降载的一类。

### 2.3 事件截图保存与上报

当前 `cleaningcar/events.py` 的事件截图链路里：

- 每次事件截图固定 resize 到 `1920x1080`
- `cv2.imwrite(..., JPEG quality=85)`
- 若 `system.api.capture_mode = base64`，还会再次读文件并 `base64.b64encode(...)`

当前正式配置里：

- `system.api.capture_mode = "base64"`

这意味着事件一旦触发，会有：

1. resize
2. JPEG 编码写盘
3. 再读盘
4. Base64 编码
5. 再随 JSON 上传

这对 CPU、磁盘和网络都不便宜。

### 2.4 Web 录像浏览与日志读取

当前 `web/server.py` 里：

- `/videos/per_id` 会 `root.rglob("*.mp4")`
- 然后按文件时间排序
- 然后还会为每个视频去 `events_root.glob(f"{key_prefix}_t5_*.json")` 追元数据

这意味着录像一多，页面每次看列表都可能触发全目录扫描。

另外：

- `/logs/inference` 直接从内存日志 buffer 取
- `/logs/events` 和 `/logs/detections` 会实时读 CSV 尾部
- `/debug_frame` 会直接回调试图

这类问题属于“Web 调试/浏览方便，但长期跑起来会有持续额外成本”。

### 2.5 中文文字渲染

当前 `cleaningcar/text_render.py` 使用：

- `Pillow`
- `ImageDraw`
- `ImageFont`

在叠字时会做：

- BGR -> RGB
- patch 转 PIL Image
- draw.text(...)
- 再转回 OpenCV BGR

这比纯 `cv2.putText(...)` 重得多。当前它已经是正确显示中文的必要方案，但从性能角度看，仍属于中后期可优化项。

### 2.6 监控与运行日志

当前 `cleaningcar/monitoring.py` 会按 `system.monitor_interval` 周期采集：

- `psutil.cpu_percent`
- `psutil.virtual_memory`
- 进程 RSS
- 温度

并打印 `[monitor] ...`

同时 `pipeline.py` 还会按 `reader_fps_log_interval` 打 `[perf] ...` 窗口性能日志。

这类开销本身通常不如录像和写图重，但会制造大量日志和轮询噪音。

### 2.7 硬解与 RGA 现状

当前仓库已经具备：

- `video.hw_decode`
- `GStreamer + mpp` 的硬解读流入口

但这是板端相关能力，不适合默认强开。

RGA 方面：

- 正式主链路尚未接入
- 当前仓库也没有完整 RGA 运行产物

因此 RGA 属于高收益但高风险项，不能排在第一批。

## 3. 先按“最方便先做”排序

这一部分强调：

- 尽量少改代码
- 或者先用现成配置开关降低开销

### 第 1 位：收紧调试输出

建议动作：

- 非调试阶段关闭或弱化 `video.debug_frame_path`
- 提高 `video.debug_frame_interval`
- 关闭 `logic.debug_overlay`
- 关闭 `logic.debug_track_state`
- 关闭 `logic.debug_anchor_points`
- 关闭 `logic.debug_water_boxes`

原因：

- 不碰核心推理
- 改动最小
- CPU、JPEG 编码、磁盘 I/O、前端轮询压力会立刻下降

建议级别：

- 立即可做

### 第 2 位：先把 `per_id` 录像参数降载

建议动作：

- 下调 `logic.per_id_target_width` / `logic.per_id_target_height`
- 或直接引入/启用更明确的缩放比例策略
- 提高 `logic.per_id_frame_stride`
- 下调 `logic.per_id_fps`
- 非必要时临时关闭 `logic.enable_per_id_video`

原因：

- 这是当前持续性重负载之一
- 参数已具备，不一定要先改架构
- 对功能影响是“录像画质/帧率变化”，不是业务逻辑变化

建议级别：

- 立即可做

### 第 3 位：把事件截图上报从 `base64` 改成 `path`

建议动作：

- 正式环境优先用 `system.api.capture_mode = path`

原因：

- 少一次读盘
- 少一次 Base64 编码
- 减小事件 JSON 体积
- 对 CPU、网络和上传端压力都有帮助

前提：

- 甲方接口链路必须接受路径模式，或者允许你们自行传文件路径/文件服务地址

建议级别：

- 如果接口允许，立即可做

### 第 4 位：降低监控与性能日志频率

建议动作：

- 提高 `system.monitor_interval`
- 提高 `reader_fps_log_interval`
- 后续把性能摘要改成低频汇总或按按钮查看

原因：

- 代码风险低
- 有利于精简日志
- 对长时间运行和问题排查更友好

建议级别：

- 立即可做

### 第 5 位：优先确认 `video.hw_decode` 能否稳定启用

建议动作：

- 仅在目标板端单独验证后启用

原因：

- 这是少数可能直接明显降低解码 CPU 的现成开关
- 但和板端 GStreamer/mpp 环境强相关

建议级别：

- 可并行评估，但不要默认强开

## 4. 再按“性价比 / 优化力度”排序

这一部分强调：

- 值不值得专门开发
- 做完之后对整体运行压力的改善是否明显

## 第一梯队：建议优先开发

### 1. 调试链路瘦身

涉及文件：

- `cleaningcar/pipeline.py`
- `web/server.py`
- `web/templates/zone_editor.html`
- `web/helpers.py`

建议目标：

- 调试帧默认关闭或手动刷新
- 日志默认只展示关键事件和低频性能摘要
- Web 不再高频依赖文件轮询

收益：

- 开发成本低
- 风险低
- 对 CPU、磁盘、Web 响应都有直接收益

综合评价：

- 性价比最高

### 2. 单车录像降载与分级策略

涉及文件：

- `cleaningcar/pipeline.py`
- `cleaningcar/video_io.py`
- `web/config_tiers.py`
- `web/templates/zone_editor.html`

建议目标：

- 提供“正式模式 / 调试模式”的 `per_id` 参数档位
- 默认不再强绑 1080p + 20fps + stride=1
- 必要时按 CPU 水位或配置做更明确的降载

收益：

- 对持续运行最有效
- 不改事件逻辑
- 可逐步收口

综合评价：

- 高收益，高可控，建议排第一批开发

### 3. Web 录像浏览索引化

涉及文件：

- `web/server.py`
- `web/helpers.py`
- `web/templates/zone_editor.html`
- `cleaningcar/events.py` 或录像收尾落盘逻辑

建议目标：

- 不再每次 `/videos/per_id` 都全盘 `rglob`
- 建录像索引
- 支持分页、筛选、最近记录优先

收益：

- 视频积累越多，收益越明显
- 能明显改善 Web 卡顿和后端文件扫描

综合评价：

- 中低风险，高实用价值

### 4. 事件截图链路收紧

涉及文件：

- `cleaningcar/events.py`
- `web/config_tiers.py`
- `web/templates/zone_editor.html`

建议目标：

- 允许正式模式不用 `base64`
- 事件截图分辨率从固定 `1920x1080` 改为可配置
- 截图质量和是否保存原图进一步收口

收益：

- 对事件频繁场景很有价值
- CPU、I/O、网络一起减负

综合评价：

- 中低风险，建议第一梯队

## 第二梯队：中等改动，中高收益

### 5. 中文叠字与画框渲染优化

涉及文件：

- `cleaningcar/text_render.py`
- `cleaningcar/pipeline.py`
- `cleaningcar/worker.py`

建议方向：

- 仅中文走 Pillow，ASCII 统一走 `cv2.putText`
- 频繁重复标签做缓存
- 调试叠字和业务叠字分开开关

收益：

- 对高帧率运行有帮助
- 尤其在中文车型、车牌、省份字较多时有效

风险：

- 容易引入显示回退问题

综合评价：

- 值得做，但不建议先于调试链路和录像链路

### 6. 帧拷贝与缓存路径减负

涉及文件：

- `cleaningcar/pipeline.py`
- `cleaningcar/worker.py`

当前可见现状：

- `frame.copy()`
- `latest_raw_frame`
- `latest_annotated_frame`
- `raw_frame_cache`
- 写录像前再次 resize / copy

建议方向：

- 只在真正需要时复制帧
- 原图、标注图、截图图分离懒生成
- 减小 `raw_frame_cache` 生命周期

收益：

- 对内存和 CPU 都有帮助

风险：

- 会碰到主链路的数据共享与时序问题

综合评价：

- 值得做，但需要小心验证

### 7. 监控和性能统计产品化

涉及文件：

- `cleaningcar/monitoring.py`
- `cleaningcar/pipeline.py`
- `web/server.py`

建议方向：

- 由“持续刷日志”改为“低频摘要 + 手动查看”
- 让 `/inference/status` 和 `/inference/health` 成为主要查看入口

收益：

- 主要提升运维体验和日志可读性

综合评价：

- 不是最大性能项，但值得配合第一梯队一起做

## 第三梯队：高收益但高风险专项

### 8. 硬解稳定接入

涉及文件：

- `cleaningcar/video_io.py`
- `configs/*.json`
- 板端 GStreamer / mpp 环境

收益：

- 对 RTSP 解码 CPU 可能有明显收益

风险：

- 强依赖板端环境
- 失败时可能直接起不来流

综合评价：

- 适合单独做板端验证，不适合和普通代码优化混做

### 9. RGA 缩放接入

专项文档：

- `RGA启用与兼容性评估计划.md`

收益：

- 如果成功接入检测前处理，理论上有明显缩放收益

风险：

- 当前主链路未接
- 当前仓库缺运行产物
- 板端 ABI / so / 驱动差异很大

综合评价：

- 高收益高风险，必须后置

### 10. 推理主链路结构级优化

例如：

- 工人线程/队列模型调整
- 模型前后处理重构
- 更激进的 ROI 裁剪
- 异步截图/异步录像写盘队列

收益：

- 上限高

风险：

- 最容易碰功能稳定性
- 最容易引入事件、截图、录像不同步

综合评价：

- 不建议在当前稳定基线下优先动

## 5. 当前最推荐的开工顺序

如果按“先稳、再快、再重构”的顺序，我建议这样排：

1. 调试链路瘦身
2. 单车录像降载与参数档位
3. 事件截图链路收紧，优先评估 `base64 -> path`
4. Web 录像浏览索引化
5. 中文叠字与日志展示优化
6. 硬解专项验证
7. RGA 专项验证与接入
8. 更深层的主链路重构

## 6. 哪些项可以不改代码先试

以下事项可以先板端试验，不一定要先开发：

- 关闭或降低调试叠字
- 提高 `video.debug_frame_interval`
- 关闭或减弱调试图输出
- 下调 `logic.per_id_fps`
- 提高 `logic.per_id_frame_stride`
- 下调 `logic.per_id_target_width` / `logic.per_id_target_height`
- 非必要时关闭 `logic.enable_per_id_video`
- 提高 `system.monitor_interval`
- 提高 `reader_fps_log_interval`
- 单独验证 `video.hw_decode`
- 若接口允许，切到 `system.api.capture_mode = path`

这些是最适合先拿板端做 A/B 对比的项。

## 7. 哪些项暂时不建议先动

以下事项不建议作为第一批：

- 直接改动检测阈值来“换性能”
- 直接减少 worker 数量而不做板端对比
- 一上来就做 RGA 正式接入
- 一上来就重构事件、截图、录像的主时序
- 在未确认板端环境前默认强开硬解

原因很简单：

- 这些项不是风险最高，就是最容易影响现有功能口径

## 8. 建议的验收指标

后续每做一项优化，都建议固定看这几类指标：

- `/inference/health` 是否持续 `ok`
- `restart_count` 是否异常增长
- 心跳帧号是否持续推进
- 事件是否仍正常触发
- 截图是否仍正常生成
- `per_id` 录像是否仍正常保留
- CPU、RSS、温度是否下降
- 单路 RTSP 或本地视频的整体 FPS 是否稳定

## 9. 当前建议

如果你要开始一项一项慢慢做，我建议从下面 3 项中选第一项开工：

1. 调试链路瘦身
2. 单车录像降载与参数档位
3. 事件截图链路收紧

这三项共同特点是：

- 风险低
- 收益直接
- 板端容易验证
- 失败也容易回退
