# 项目解耦报告

## 目标

在不改变现有功能、入口方式、配置结构、HTTP 路由和事件输出行为的前提下，将原先集中在大文件中的逻辑拆分为职责清晰的模块，便于维护、扩展和部署。

## 当前解耦结果

### 1. 检测主链路拆分到 `cleaningcar/`

主运行代码已经拆成独立模块：

- `cleaningcar/constants.py`
  - 全局常量、类别定义、阈值和标签映射
- `cleaningcar/runtime_config.py`
  - 配置加载、默认配置路径、CLI 覆盖
- `cleaningcar/video_io.py`
  - 视频源打开、运行时路径解析、FFmpeg 写出
- `cleaningcar/vision.py`
  - ROI 缩放、几何辅助、IoU 计算
- `cleaningcar/fp_detect.py`
  - FP 检测模型后处理
- `cleaningcar/plate_lpr.py`
  - 双模型车牌识别主链路
- `cleaningcar/plate.py`
  - 车牌文本规范化、合法性校验和锁定
- `cleaningcar/text_render.py`
  - 中文渲染层
- `cleaningcar/tracking.py`
  - 车辆跟踪
- `cleaningcar/events.py`
  - 事件状态机、截图输出、上报封装
- `cleaningcar/runtime_signals.py`
  - 心跳、启动信号、命令目录截图
- `cleaningcar/storage_cleanup.py`
  - 运行产物保留策略
- `cleaningcar/worker.py`
  - RKNN 检测 worker 和双模型车牌识别执行层
- `cleaningcar/pipeline.py`
  - 主流程编排和结果汇总
- `cleaningcar/cli.py`
  - 命令行参数与启动装配

### 2. Web 控制层拆分到 `web/`

- `web/state.py`
  - Web 运行状态、默认路径和缓存
- `web/models.py`
  - Web 请求模型
- `web/inference.py`
  - 推理 guardian、自启、健康检测、日志缓存
- `web/helpers.py`
  - 配置读取、路径解析、日志和调试帧读取
- `web/server.py`
  - FastAPI 路由和应用装配

### 3. 部署入口从“多脚本混杂”解耦为 4 个固定入口

当前根目录只保留：

- `install_runtime_venv.sh`
  - 只负责安装环境
- `start_web_server.sh`
  - 只负责手工管理 Web
- `uninstall_runtime_venv.sh`
  - 只负责卸载环境并清理 systemd 服务
- `install_cleaningcar_systemd.sh`
  - 只负责安装 `cleaningcar-web.service`

对应收益：

- 环境安装、手工运行、卸载、服务化边界清晰
- 板端交付不再需要记忆多个用途重叠的 `.sh`

## 本轮新增解耦点

### 1. FP 检测后处理策略解耦

检测模型后处理不再写死成单一路径，而是通过独立配置项切换：

- `video.fp_output_mode=6`
  - 默认模式
  - 9 输出模型也按 `box + class` 方式解析
- `video.fp_output_mode=9`
  - 使用 `box + class + score`

结果：

- 模型输出结构和业务主流程进一步解耦
- 同一个检测模型可以在两种解析方式之间一键切换

### 2. 车牌推理与文本后处理解耦

- `cleaningcar/plate_lpr.py`
  - 只负责双模型车牌推理
- `cleaningcar/plate.py`
  - 只负责规范化、合法性校验、锁定

结果：

- 推理链路和锁定链路边界更清晰
- 当前主链路只保留双模型，不再混入旧单模型 LPR

### 3. 运行信号与主业务解耦

- 心跳、启动信号、手动截图命令由 `cleaningcar/runtime_signals.py` 负责
- 健康检测与推理自启由 `web/inference.py` 负责

### 4. 运行产物清理解耦

- `cleaningcar/storage_cleanup.py` 独立负责截图与单车视频清理
- 主流程只在 `pipeline.py` 里周期调用，不把清理逻辑散落到事件、截图或视频模块里
