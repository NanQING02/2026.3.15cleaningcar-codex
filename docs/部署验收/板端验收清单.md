# 板端验收清单

这份清单用于把当前版本在 RKNN 板端做一次完整验收，重点确认 6 件事：

1. 环境安装流程清晰可复现
2. Web 服务可稳定启动
3. 主检测链路可正常运行
4. 双模型车牌链路可正常运行
5. 心跳 / guardian / 自动恢复可正常生效
6. 截图、事件、单车视频和清理策略口径正确

## 1. 验收前准备

先确认以下文件存在：

- `configs/config.json`
- `models/detection/best.rknn`
- `models/plate/plate_detect.rknn`
- `models/plate/plate_rec_color.rknn`
- `fonts/platech.ttf`
- `packages/` 下 RKNN / RGA 运行依赖

先确认以下配置项已经合理：

- `video.source`
- `video.source_mode`
- `video.fp_output_mode`
- `logic.per_id_video_dir`
- `system.heartbeat_path`
- `system.startup_flag_path`
- `system.startup_capture_dir`
- `system.manual_capture_dir`
- `storage.capture_keep_days`
- `storage.capture_keep_count`
- `storage.per_id_video_keep_days`
- `storage.per_id_video_keep_count`

推荐先拿一段固定测试视频做一轮验收，再切 RTSP 实时流，这样更容易复现问题，也方便做 `6/9` 模式对比。

若甲方设备尚未补齐 `mppvideodec` 插件，本轮验收请保持：

```json
"video": {
  "hw_decode": false
}
```

相关背景见 `docs/部署验收/甲方设备MPP环境说明.md`。

## 2. 安装环境

在板端项目根目录执行：

```bash
cd /home/hinlink/3.17/2026.3.15cleaningcar-codex
chmod +x install_runtime_venv.sh start_web_server.sh uninstall_runtime_venv.sh install_cleaningcar_systemd.sh
./install_runtime_venv.sh
```

验收点：

- `venv-gst/` 创建成功
- 依赖安装过程中没有 RKNN / RGA 相关报错
- 脚本结束后不会自动拉起 Web

## 3. 启动 Web 服务

### 3.1 手工模式

```bash
cd /home/hinlink/3.17/2026.3.15cleaningcar-codex
source venv-gst/bin/activate
./start_web_server.sh start
./start_web_server.sh status
```

### 3.2 `systemd` 模式

```bash
cd /home/hinlink/3.17/2026.3.15cleaningcar-codex
./install_cleaningcar_systemd.sh
systemctl status cleaningcar-web --no-pager
```

验收点：

- 浏览器能打开 `http://板端IP:8000/`
- 首页不是 `Template missing`
- `ss -ltnp | grep :8000` 能看到服务监听
- 手工模式下 `web_server_8000.log` 会持续写日志

## 4. 启动推理

Web 服务起来后，再启动推理：

```bash
curl -X POST http://127.0.0.1:8000/inference/start
```

查看运行状态：

```bash
curl http://127.0.0.1:8000/inference/status
curl http://127.0.0.1:8000/inference/health
```

重点看这些字段：

- `running=true`
- `pid` 有值
- `heartbeat.available=true`
- `heartbeat.healthy=true`
- `heartbeat.reason=ok`
- `restart_count` 不应异常增长

## 5. 必查项

### 5.1 推理日志

```bash
curl "http://127.0.0.1:8000/logs/inference?lines=100"
curl "http://127.0.0.1:8000/logs/files"
tail -n 100 logs/inference/infer_*.log
```

重点看：

- 是否成功加载检测模型
- 是否成功加载双模型车牌识别
- 是否出现 `Expected 6 outputs ... got 9` 一类后处理报错
- 是否出现持续重启、持续掉流、持续 backpressure

### 5.2 心跳文件

默认路径：

- `/dev/shm/cleaningcar_heartbeat.json`

```bash
cat /dev/shm/cleaningcar_heartbeat.json
```

重点看：

- `status`
- `timestamp`
- `last_progress_ts`
- `latest_frame_idx`
- `reconnect_count`
- `startup_emitted`

正常情况下：

- `timestamp` 会持续刷新
- `last_progress_ts` 会持续前进
- `latest_frame_idx` 会持续增长

### 5.3 启动信号

默认标志文件：

- `/dev/shm/cleaningcar_started.flag`

默认截图目录：

- `captures/startup/`

说明：

- 这是自动启动截图
- 推理第一次真正出结果后会自动保存，不需要手工触发

```bash
cat /dev/shm/cleaningcar_started.flag
find captures/startup -type f | tail
```

验收点：

- 首次真正出结果后会生成启动标志文件
- 会保存一组启动截图
- 推理日志里能看到 `[startup-signal]`

### 5.4 手动保留截图

```bash
curl -X POST http://127.0.0.1:8000/snapshot/keep \
  -H "Content-Type: application/json" \
  -d "{\"tag\":\"board_check\",\"raw\":true,\"annotated\":true}"
```

验收点：

- 接口返回 `status=queued`
- `system.command_dir` 下命令会被消费
- 会生成 `.done.json` 结果文件
- `captures/manual/` 下会新增截图

### 5.5 事件输出与截图

```bash
find events -maxdepth 2 -type f | tail -n 20
find captures -maxdepth 3 -type f | tail -n 20
```

重点看：

- 事件 JSON 是否产出
- `event_log.csv` 是否持续追加
- 事件截图是否和事件对得上
- `captureImage` 非空且文件真实存在

### 5.6 单车视频输出

默认输出目录：

- `video_result/per_id/`

验收点：

- 当 `logic.per_id_video_dir` 留空时，不应在项目根目录生成裸的 `YYYYMMDD/HH` 空目录
- 当配置目录不可写时，应自动回退到 `video_result/per_id/`
- 若单车视频不可写，只禁用单车视频，不影响主检测、事件 JSON 和截图链路

### 5.7 双模型车牌链路

重点确认：

1. 推理日志里没有车牌模型加载失败
2. 结果中能看到车牌文本与颜色结果
3. 当前只走双模型车牌链路，不再走旧单模型 LPR
4. 车型中文和车牌省份汉字不再显示 `??`

## 6. 自启 / 卡死恢复验收

### 6.1 推理进程异常退出自启

先查推理 PID：

```bash
curl http://127.0.0.1:8000/inference/status
```

然后手动杀掉推理进程：

```bash
kill -9 <推理PID>
```

再观察：

```bash
watch -n 1 "curl -s http://127.0.0.1:8000/inference/status"
```

验收点：

- `restart_count` 增加
- `running` 会恢复成 `true`
- guardian 日志里会出现进程退出和重启记录

### 6.2 心跳超时恢复

```bash
kill -STOP <推理PID>
```

等待超过：

- `system.heartbeat_timeout_seconds`
- 或 `system.progress_timeout_seconds`

再观察：

```bash
curl http://127.0.0.1:8000/inference/health
```

验收点：

- `heartbeat.reason` 会出现 `heartbeat_stale` 或 `progress_stale`
- guardian 会终止旧进程并重启

## 7. `fp_output_mode=6/9` 对比验收

建议用同一段本地测试视频做 A/B，对比最稳定。

### 7.1 模式 6

```bash
source venv-gst/bin/activate
python run_zone_detect.py \
  --config configs/config.json \
  --video /path/to/test.mp4 \
  --source_mode file \
  --fp_output_mode 6 \
  --csv ./video_result/fp_mode6.csv
```

### 7.2 模式 9

```bash
source venv-gst/bin/activate
python run_zone_detect.py \
  --config configs/config.json \
  --video /path/to/test.mp4 \
  --source_mode file \
  --fp_output_mode 9 \
  --csv ./video_result/fp_mode9.csv
```

对比时至少看 4 件事：

1. 能否稳定跑完，不崩溃
2. 检测框数量是否明显异常
3. 误检、漏检是否变化
4. 事件类型和触发时机是否变化

当前默认策略：

- 默认 `6`
- 即使 FP 模型实际给出 `9` 个输出，也只取每个尺度的 `box + class`

## 8. 验收完成后的收口动作

通过后建议立即做这 4 件事：

1. 确认正式默认配置使用 `fp_output_mode=6` 还是 `9`
2. 保存一份通过验收的 `configs/config.json`
3. 保留一份通过验收的推理日志和关键截图
4. 再做一次版本提交

如果有一项没通过，优先保留以下信息再回传：

- `logs/inference/infer_*.log`
- `curl /inference/status` 返回值
- `curl /inference/health` 返回值
- `/dev/shm/cleaningcar_heartbeat.json`
- `/dev/shm/cleaningcar_started.flag`
