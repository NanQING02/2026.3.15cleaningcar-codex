# 后续需求实施方案

## 1. 本轮范围

本轮只实施并保留以下 3 项运行能力，其他整理项统一后置，不在本轮代码中继续展开：

1. 外部程序运行检测 / 死机自启
2. 明显启动信号
3. 保留截图命令和功能

当前状态：以上 3 项已完成代码落地，已通过本地静态校验，待 RKNN 板端联调验证。

## 2. 实施落点

### 2.1 外部程序运行检测 / 死机自启

目标：

- 推理进程持续输出运行心跳
- Web guardian 不只看“进程活着”，还看“是否真正有进展”
- 当心跳或进度超时后，自动拉起推理进程

代码落点：

- `cleaningcar/runtime_config.py`
  - 将 `system` 配置并入运行时配置，保证心跳、命令目录、启动标志等参数真实生效
  - 暴露 `config_path`、`config_name`
- `cleaningcar/cli.py`
  - 固定传递当前配置文件绝对路径和配置目录
- `cleaningcar/runtime_signals.py`
  - 统一解析运行时路径
  - 提供心跳 JSON 原子写入和读取辅助函数
- `cleaningcar/pipeline.py`
  - 推理主循环周期性写入心跳
  - 在读帧、出结果、回压等待、重连、停止等阶段写入状态
- `web/inference.py`
  - guardian 读取心跳文件
  - 检查心跳时间戳与 `last_progress_ts`
  - 超时后终止当前推理进程并按原有机制自动重启

验收点：

- 推理运行时会持续刷新心跳文件
- 相机卡住或主循环无进度超过阈值时，guardian 会记录异常并重启推理
- `GET /inference/status` 和 `GET /inference/health` 可看到心跳状态

### 2.2 明显启动信号

目标：

- 系统真正进入“已出结果”状态后，给出可见、可轮询、可留痕的启动信号

代码落点：

- `config_manager.py`
  - 补齐启动标志、启动截图、心跳等默认配置项
- `cleaningcar/runtime_signals.py`
  - 提供截图保存能力
- `cleaningcar/pipeline.py`
  - 第一次成功产出处理结果后：
    - 写入明显日志 `[startup-signal] ...`
    - 写入启动标志文件
    - 自动保存启动截图到 `captures/startup/...`

信号形式：

- 日志信号：控制台 / 推理日志中出现 `[startup-signal]`
- 文件信号：`system.startup_flag_path`
- 画面信号：`system.startup_capture_dir`

验收点：

- 推理第一次真正跑通后会生成启动截图
- 启动标志文件中包含时间、配置名、帧号、截图路径

### 2.3 保留截图命令和功能

目标：

- 保留运行中人工触发截图的能力
- 支持外部程序写命令文件触发
- 支持 Web 接口触发
- 同时保留原图和标注图

代码落点：

- `cleaningcar/runtime_signals.py`
  - 生成截图命令文件
  - 保存截图到 `captures/manual/...`
- `cleaningcar/pipeline.py`
  - 缓存最新可用帧
  - 轮询 `system.command_dir` 下的 `*.cmd.json`
  - 识别 `keep_snapshot` 命令
  - 生成 `.done.json` / `.failed.json` 处理结果
- `web/models.py`
  - 新增 `SnapshotKeepPayload`
- `web/server.py`
  - 新增 `POST /snapshot/keep`

命令格式：

```json
{
  "cmd": "keep_snapshot",
  "tag": "manual",
  "raw": true,
  "annotated": true
}
```

验收点：

- 向命令目录放入 `*.cmd.json` 后，可生成保留截图
- 调用 Web 接口后，会先写入命令文件，再由推理进程处理
- 处理结果会落到同目录下的 `.done.json` 或 `.failed.json`

## 3. 新增 / 使用的配置项

以下配置位于 `configs/*.json` 的 `system` 节点中：

- `command_dir`
- `startup_flag_path`
- `heartbeat_path`
- `heartbeat_interval_seconds`
- `heartbeat_timeout_seconds`
- `progress_timeout_seconds`
- `heartbeat_startup_grace_seconds`
- `startup_capture_dir`
- `manual_capture_dir`

如未显式配置，会使用 `config_manager.py` 中的默认值。

### 相关基础调整

本轮同时补充了检测模型后处理切换能力，位于 `video.fp_output_mode`：

- `6`
  - 默认值
  - 9 输出模型也只使用 `box + class`
- `9`
  - 使用 `box + class + score`

该项用于对比不同后处理方式，不影响本轮 3 项运行能力的边界。

## 4. 建议验证步骤

### 4.1 静态验证

```bash
python -m py_compile cleaningcar/runtime_config.py cleaningcar/cli.py cleaningcar/runtime_signals.py cleaningcar/pipeline.py web/models.py web/server.py web/inference.py
```

### 4.2 配置验证

```bash
python -c "from cleaningcar.runtime_config import load_config; cfg = load_config('configs/config.json'); print(cfg['system']['heartbeat_path']); print(cfg['config_name'])"
```

### 4.3 运行验证

1. 启动 Web 和推理
2. 观察日志中是否出现 `[startup-signal]`
3. 检查启动截图目录和启动标志文件
4. 调用 `POST /snapshot/keep` 或写入命令文件，检查手动截图是否生成
5. 调用 `/inference/status`，检查 `heartbeat` 字段是否正常更新

## 5. 本轮不做

本轮不继续做脚本拆分、systemd 模板化、配置清单化、CLI 参数收口等整理动作，已单独记录在 `docs/后置项记录.md`。
